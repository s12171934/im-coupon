# 가게 벡터 모델

> 개인화 신호가 읽는 **가게 벡터를 무엇으로 어떻게 만드는가**의 SSOT.
> 임베딩 모델 선정, 벡터에 들어가는 구성 요소, 텍스트에서 384차원 벡터가 나오기까지의 단계가 여기 있다.
> **생성 로직은 이 저장소의 코드로 들어가지 않는다.** 저장소에는 시연에 쓸 벡터 데이터만 커밋하고, 그 데이터를 만든 로직과 조건은 이 문서가 기록한다.
> 벡터를 **쓰는** 쪽의 계약은 [KAN-24 기획 명세](KAN-22/personal-fit-spec.md) 와 [로직과 노드 흐름](KAN-22/personal-fit-flow.md) 이다.
> 갱신 — 2026-09-14

## 이 문서의 범위

`personalFitSignal` 은 가게 벡터를 외부에서 받아 계산만 한다. 그 벡터를 만드는 일이 이 문서의 대상이다.

- 포함 — 모델 선정과 근거, 벡터 구성 요소, 전처리, 임베딩 단계, 버전 식별자, 커밋한 데이터의 구성.
- 제외 — **임베딩 생성 코드**. 모델 로딩·추론·배치 처리는 이 저장소에 두지 않는다.
- 제외 — 사용 사건 수집과 실제 사용자 귀속, 발급 서비스에 신호를 등록하는 일, 추천 이유 문장, 화면.
- 제외 — 임베딩 미세조정. 모델 가중치는 고정하고 시민 프로필만 갱신한다.
- 산출물 — `apps/api/src/issuance/domain/signals/implementations/personal-fit-input.ts` 의 `PersonalFitMerchantVector` 레코드다.
- 산출 필드 — `merchantId`, `contentVersion`, `specId`, `knownAt`, `verifiedAt`, `values[]` 여섯이다.
- 실행 티켓 — [KAN-25 가게 별 벡터 데이터 생성](https://ssong9520.atlassian.net/browse/KAN-25).
- 코드를 두지 않는 이유 — 생성은 데이터가 바뀔 때만 도는 일회성 배치다. 약 470MB 가중치와 추론 런타임을 프로토타입 의존성에 넣으면 설치·기동 비용이 시연 전체에 걸린다.
- 대신 두는 것 — 생성 결과인 벡터 데이터를 `data/seed/` 에 커밋한다. 재생성이 필요하면 이 문서의 조건과 단계를 따라 저장소 밖에서 돌린 뒤 데이터만 교체한다.

## 모델 선정

| 후보 | 차원 | 라이선스 | Node 실행 | 판정 |
| --- | --- | --- | --- | --- |
| `intfloat/multilingual-e5-small` | 384 | MIT | ONNX 기성 미러 있음 | 채택 |
| `intfloat/multilingual-e5-base` | 768 | MIT | 가능 | 기각 |
| `dragonkue/multilingual-e5-small-ko` | 384 | Apache-2.0 | ONNX 직접 변환 필요 | 보류 |
| `BAAI/bge-m3` 계열, `nlpai-lab/KURE-v1` | 1024 | 별도 확인 필요 | 변환 필요, 가중치 큼 | 기각 |
| OpenAI `text-embedding-3-small` | 1536 | API 이용약관 | 외부 전송 | 기각 |

채택 근거는 넷이다.

- 저장소가 순수 TypeScript·Node 모노레포다. 파이썬 사이드카 없이 추론하려면 ONNX 가중치가 기성으로 있어야 한다.
- 입력이 `업종 + 메뉴 5개` 로 30토큰 안팎이다. 장문 검색 성능과 큰 차원은 이 입력에서 회수되지 않는다.
- 제출 서약이 외부 도구의 이용약관·라이선스 준수를 요구한다. MIT 가중치가 설명 부담이 가장 낮다.
- 접수 마감이 2026-09-20이다. 변환·양자화 실험에 쓸 시간이 없다.

기각·보류 근거는 아래와 같다.

- `multilingual-e5-base` — 차원만 두 배이고 입력이 짧아 이득이 없다. 저장 용량과 추론 시간만 늘어난다.
- `dragonkue/multilingual-e5-small-ko` — 한국어 파인튜닝판이며 같은 384차원이다. 공식 ONNX 산출물이 없어 변환 단계에서 파이썬 도구가 다시 들어온다.
- `bge-m3`·`KURE-v1` — 강점이 장문 검색이다. 이 입력에 쓰이지 않는 강점에 가중치 크기를 지불하게 된다.
- OpenAI — 가게 설명을 외부로 보내고, 2026-10-22 본선 시연이 현장 네트워크와 API 가용성에 매인다.

교체 경로는 열려 있다. `dragonkue/multilingual-e5-small-ko` 는 차원이 같아 산출 계약이 바뀌지 않는다. 바뀌는 것은 `specId` 와 전 벡터 재생성뿐이다.

## 확정 모델의 사실

2026-09-14에 모델 카드, `config.json`, npm 메타데이터를 직접 읽어 확인한 값이다.

- 모델 — `intfloat/multilingual-e5-small`. 라이선스 MIT, 100개 이상 언어 지원.
- 구조 — `num_hidden_layers` 12, `hidden_size` 384, `max_position_embeddings` 512, `vocab_size` 250,037.
- 규모 — 약 117.65M 파라미터. fp32 가중치는 약 470MB다.
- 출력 — 384차원 실수 벡터 하나.
- 접두어 규약 — E5 계열은 입력에 `query: ` 또는 `passage: ` 접두어를 요구한다.
- 실행 산출물 — `Xenova/multilingual-e5-small` 미러의 `onnx/model.onnx`. revision 은 `761b726dd34fb83930e26aab4e9ac3899aa1fa78` 로 고정한다.
- 미러의 라이선스 — 미러 저장소는 라이선스 필드를 선언하지 않는다. 권리 근거는 원본의 MIT이며 서류에 적을 때 이 사실을 함께 적는다.
- 런타임 — `@huggingface/transformers` 4.2.0(Apache-2.0). `onnxruntime-node` 1.24.3을 함께 들여온다.

## 현재 시드 — 2026-09-15 대전 공공 상가로 교체

- 기존 가상 가게 12곳·벡터 13건을 실제 대전 상가 12곳·벡터 12건으로 교체했다. 아래 2026-09-14 기록은 교체 전 조사·실험 이력이다.
- D1 `storeListInDong`의 대전(`30`) 첫 페이지 100건에서 서로 다른 12개 업종의 첫 유효 상가를 선택했다. 조회 기준월은 202606, 대전 전체 건수는 80,704다. 대표성을 보장하는 표본은 아니다.
- 실제 상호·지점명·업종·구군·행정동·주소·좌표·상가업소번호를 저장한다. 원천 응답과 선정 방법은 `data/sources/daejeon-stores.json`에 있다.
- 입력은 `query: 지역: {구군} {행정동}. 업종: {API 업종명}.`이다. API에 없는 대표메뉴는 빈 배열로 두며 기존 목 메뉴를 붙이지 않는다.
- 기존과 동일한 E5 revision `761b726dd34fb83930e26aab4e9ac3899aa1fa78`, fp32, mean pooling, L2 정규화로 전 벡터를 다시 생성했다. 384차원·단위 노름 조건은 생성 단계에서 확인했다. 기존 가게쌍의 코사인 실측값은 새 데이터의 결과가 아니다.
- 생성은 저장소 밖 일회성 배치이며 앱 의존성은 늘리지 않았다. Transformers 4.2.0의 로컬 모델 경로로 로드하고 같은 revision의 토크나이저를 명시적으로 연결했다.
- 새 버전의 알려진 시각·벡터 생성 시각을 기록하고 그 이후 시각으로 가상 소비 이력 120건을 재생성했다. 새 설명으로 과거 실제 거래를 소급한 것이 아니다.

### 결론

- 지금 확보한 데이터만으로 만들 수 있는 것은 **업종별 벡터 11개**다. 가게별 벡터가 아니다.
- 같은 업종의 가게는 전부 같은 벡터를 갖는다. 개인화 신호가 가게를 가르지 못하고 업종 선호 신호로 축소된다.
- **대표메뉴와 좌표가 서로 다른 원천에 있다.** 착한가격업소에는 메뉴가 있고 좌표가 없으며, 상가(상권)정보에는 좌표가 있고 메뉴가 없다.
- 두 원천에 공통 식별자가 없다. 상호명과 주소를 정규화해 맞추는 수밖에 없고, 이 매칭의 정확도가 벡터 품질의 상한이 된다.
- 착한가격업소는 대구광역시 전용 데이터셋이라 대상 지역과 정확히 겹친다. 매칭 대상 모수가 그만큼 작아진다.
- 인증키 발급이 두 원천 모두의 단일 선행 조건이다.

## 벡터 구성 요소

벡터가 답하는 질문은 "이 가게가 어디에서 무엇을 파는 곳인가" 다. 임베딩 문장에 들어가는 요소는 셋이고, 벡터 레코드에 함께 실리되 문장에는 넣지 않는 요소가 하나 있다.

| 요소 | 문장에서의 자리 | 원천 |
| --- | --- | --- |
| 지역 라벨 | `지역: {구군} {행정동}` | 상가(상권)정보의 시군구·행정동, 착한가격업소의 구군·주소 |
| 업종 라벨 | `업종: {값}` | 공모전 제공 CSV의 `TP_BUZ_NM`(11종), 상가(상권)정보의 업종 소분류, 시드의 `category` |
| 대표메뉴 최대 5개 | `대표메뉴: {값}; …` | 착한가격업소의 대표메뉴. **현재 미확보** — 시연용 목 데이터로 채운다 |

| 비텍스트 요소 | 저장 위치 | 쓰임 |
| --- | --- | --- |
| 좌표 `lat`·`lon` | 가게 내용 레코드의 수치 필드 | 거리 성분. 임베딩 문장에는 넣지 않는다 |

- 최종 문장 — `query: 지역: 중구 성내2동. 업종: 분식. 대표메뉴: 김밥; 떡볶이; 우동.`
- 메뉴가 없을 때 — `query: 지역: 중구 성내2동. 업종: 분식.` 으로 조립한다. 같은 동·같은 업종 가게가 같은 벡터를 갖는다.
- 지역 라벨을 넣는 이유 — 쿠폰 사용처는 생활권 안에서 고르게 된다. 같은 동네의 가게가 서로 가까워지는 것이 추천에서 의미를 갖는다.
- 지역 라벨을 행정동까지만 두는 이유 — 번지·건물번호·상세주소의 숫자는 의미를 만들지 않고 토큰만 늘린다.
- 좌표를 문장에 넣지 않는 이유 — 위경도 숫자 문자열은 의미 벡터에 잡음으로 들어간다. `35.87` 과 `35.88` 의 근접을 임베딩이 거리로 읽지 않는다.
- 좌표를 그래도 보존하는 이유 — 실제 거리 계산과 반경 필터가 좌표를 요구한다. 벡터와 같은 내용 버전에 묶어 두어야 시점이 어긋나지 않는다.
- 업종 라벨을 넣는 이유 — 모든 가게가 반드시 갖는 유일한 공통 속성이다.
- 대표메뉴를 넣는 이유 — 같은 업종 안에서 가게를 가르는 유일한 요소다.
- 메뉴 상한이 5개인 이유 — 목록이 길수록 평균이 업종 일반으로 수렴해 가게 사이의 차이가 흐려진다.
- 희석 주의 — 평균 풀링이라 지역 라벨의 토큰이 업종·메뉴의 비중을 낮춘다. 지역 포함 전후의 순위 변화를 검증에서 측정해야 한다.

제외한 요소와 이유는 아래와 같다.

| 제외 요소 | 이유 |
| --- | --- |
| 상호명 | 브랜드 문자열이 의미를 지배한다. `별빛분식` 과 `별빛세탁소` 가 가까워진다 |
| 번지·건물번호·상세주소 | 숫자와 건물명은 의미를 만들지 않고 토큰만 늘린다. 지역 라벨은 행정동까지만 쓴다 |
| 대표메뉴 가격 | 금액 크기를 취향으로 읽지 않는다는 채점 규칙과 어긋난다 |
| 영업시간·휴무 | 시점 조건이다. 벡터가 아니라 후보 필터가 맡는다 |
| 착한가격업소 여부 | 운영자 지정 우선도가 맡는 축이다 |
| 매출·방문 규모 | 상권 회복과 이용 실적이 맡는 축이다 |
| 광고 문구·소개글 | 작성자마다 길이와 어휘가 달라 가게 사이의 비교가 불안정해진다 |

두 가지 공통 원칙이 이 제외를 만든다.

- 다른 신호가 이미 맡은 축은 벡터에 넣지 않는다. 넣으면 가중합에서 같은 근거가 두 번 계산된다.
- 시점에 따라 변하는 값은 넣지 않는다. 과거 시점의 벡터를 재현할 수 없게 된다.

## 임베딩 단계

1. **입력 수집** — `merchantId`, `regionLabel`, `categoryLabel`, `representativeMenus[]`, `lat`, `lon` 을 읽는다.
2. **정규화** — Unicode NFC를 적용하고 제어문자를 지운다. 연속 공백을 하나로 줄이고 앞뒤를 자른다.
3. **업종 라벨 정규화** — 원천의 업종명을 11종 매핑 사전으로 표준 표기에 맞춘다. `편 의 점` → `편의점` 처럼 라벨 안의 공백을 없앤다.
4. **메뉴 정리** — 각 메뉴를 정규화한 뒤 빈 값을 버리고 중복을 지운다. 코드포인트 오름차순으로 정렬해 앞에서 5개만 남긴다.
5. **지역 라벨 조립** — 시군구명과 행정동명을 `{구군} {행정동}` 으로 잇는다. 번지·건물번호·상세주소는 버린다.
6. **문장 조립** — `query: 지역: {지역}. 업종: {업종}. 대표메뉴: {m1}; {m2}; ….` 로 채운다. 메뉴가 없으면 대표메뉴 절을 뺀다.
7. **버전 산출** — 조립한 문자열의 SHA-256을 `textHash` 로 두고, 앞 12자를 붙여 `contentVersion` 을 `c1-<12자>` 로 만든다.
8. **토크나이즈** — 모델의 `tokenizer.json` 으로 자른다. `max_length` 512에 truncation을 켜고, 배치는 최장 길이에 맞춰 패딩한다.
9. **순전파** — 12층 encoder를 통과시켜 `[배치, 토큰수, 384]` 의 마지막 은닉 상태를 얻는다.
10. **평균 풀링** — attention mask를 곱해 더한 뒤 mask 합으로 나눈다. `CLS` 토큰 풀링이 아니다.
11. **L2 정규화와 검증** — 벡터를 자기 노름으로 나눈다. 차원 384, 전 성분 유한, 노름 1(오차 `1e-6` 이내)을 확인하고 `verifiedAt` 을 기록한다.
12. **좌표 보존** — `lat`·`lon` 을 같은 내용 버전의 수치 필드로 저장한다. 값이 없으면 `null` 로 두고 벡터는 그대로 유효하다.

각 단계가 왜 그 모양인지는 아래와 같다.

- 3단계가 필요한 이유 — CSV의 업종명 11종 중 `편 의 점`·`슈퍼 마켓`·`제 과 점` 셋에 낱자 사이 공백이 들어 있다. 그대로 토크나이즈하면 한 낱말이 조각으로 갈려 의미가 흐려진다.
- 3단계를 블라인드 규칙이 아니라 사전으로 두는 이유 — 값이 11개뿐이라 전수 검토가 가능하다. 공백을 무조건 지우는 규칙은 다른 원천이 들어올 때 정상 라벨을 훼손한다.
- 4단계의 정렬 — 원천에서 메뉴 순서가 바뀌어도 같은 문자열이 나와야 한다. 그래야 같은 내용이 같은 `contentVersion` 을 받는다.
- 5단계의 절단 — 지역 라벨을 행정동까지만 두어 숫자 토큰이 평균을 흔들지 않게 한다.
- 6단계의 접두어 — 가게 설명끼리의 대칭 비교이므로 양쪽 모두 `query: ` 다. `passage: ` 를 쓰지 않는다.
- 6단계의 절 순서 — 지역·업종·대표메뉴 순서를 고정한다. 평균 풀링이라 순서의 영향은 작지만 같은 내용이 같은 `contentVersion` 을 받으려면 고정이 필요하다.
- 7단계의 순서 — 정규화보다 해시를 먼저 구하면 같은 내용이 다른 버전을 받는다. 2~6단계는 7단계보다 반드시 앞이다.
- 8단계의 상한 — 실제 입력은 30토큰 안팎이라 512에서 잘릴 일이 없다. 상한은 이상 입력에 대한 방어다.
- 10단계의 mask — 패딩 토큰이 평균에 섞이면 같은 문장도 배치 구성에 따라 다른 벡터가 나온다.
- 11단계 이후 — 모든 벡터가 단위 벡터이므로 이후 코사인 유사도는 내적 한 번으로 끝난다.
- 12단계가 벡터 뒤인 이유 — 좌표는 임베딩에 들어가지 않으므로 벡터 값에 영향을 주지 않는다. 다만 같은 `contentVersion` 에 묶여야 시점이 어긋나지 않는다.

## 버전 식별자와 결정성

- `specId` 형식 — `e5s-<모델 revision 앞 8자>-<전처리 버전>-<풀링>-<dtype>`.
- 첫 값 — `e5s-761b726d-p1-meanL2-fp32`.
- `specId` 가 필요한 이유 — 명세가 다른 벡터끼리는 내적이 의미를 갖지 않는다. 한 준비 요청에 쓰이는 벡터는 전부 같은 값이어야 한다.
- dtype — `fp32` 로 고정한다. 미러에는 `int8`·`fp16`·`q4` 변형이 함께 있으나 쓰지 않는다.
- dtype이 식별자에 들어가는 이유 — 양자화는 같은 문장에서 다른 값을 낸다.
- 전처리 버전 — 첫 값은 `p1` 이다. 정규화·정렬·상한 규칙이 바뀌면 올린다.
- 재현 판정 — 같은 입력·revision·dtype이면 같은 벡터를 기대한다. 부동소수 누적 순서 차이가 남을 수 있어 완전 일치가 아니라 코사인 `1 - 1e-6` 이상으로 판정한다.
- 재생성 범위 — 모델 revision이나 전처리 버전이 바뀌면 과거 내용 버전까지 전부 다시 만든다. 명세 혼재는 곧 해당 요청의 신호 비활성이다.

### 시연이 보여줄 수 있는 사례

- 같은 동·같은 업종, 다른 메뉴 — `mer-001` 분식과 `mer-006` 분식이 중구 성내2동에 함께 있다.
- 같은 가게의 내용 변경 — `mer-001` 이 내용 버전 둘을 갖는다. 과거 버전은 `knownAt` 이 2026-06-01이다.
- 다른 업종, 겹치는 메뉴 — `mer-003` 카페와 `mer-009` 제과점이 치즈케이크를 공유한다.
- 메뉴 없는 가게 — `mer-002` 서점, `mer-004` 꽃집, `mer-005` 세탁소, `mer-011` 편의점, `mer-012` 슈퍼마켓.
- 업종 라벨 정규화 — `mer-009`·`mer-011`·`mer-012` 의 원천 표기가 `제 과 점`·`편 의 점`·`슈퍼 마켓` 이며 표준 표기로 바뀌어 임베딩됐다.

- 그래서 `0.87` 을 "관련 없음" 으로, `0.97` 을 "매우 관련 있음" 으로 읽지 않는다. 의미를 갖는 것은 같은 요청 안에서의 **상대 순위**다.
- 화면이나 서류에 이 값을 백분율·확률·만족도로 표시하지 않는다.

## 실행 환경

- 실행 위치 — 이 저장소 밖의 일회성 작업이다. 저장소에는 생성 결과만 들어온다.
- 실행 시점 — 발급 요청 경로가 아니라 사전 배치다. 점수 조회가 동기 함수라 추론이 요청 안에 들어갈 자리가 없다.
- 재생성이 필요한 때 — 업종·메뉴·행정동 변경, 전처리 버전 변경, 모델 revision 변경, dtype 변경이다.

- 재생성 절차 — 이 문서의 임베딩 단계를 그대로 따라 저장소 밖에서 돌리고, `data/seed/` 의 두 파일만 교체한다.

- 오프라인 — 캐시가 찬 뒤에는 원격 조회를 끈다. 2026-10-22 본선 시연이 현장 네트워크에 매이면 안 된다.
- 시드 데이터 조치 — 시드 가맹점에 `representativeMenus` 를 목 데이터로 채운다. 실제 자료는 착한가격업소 조인으로 마지막에 교체한다. 목 데이터 방침은 [프로토타입 범위](프로토타입-범위.md) 를 따른다.
- 현재 상태 — 2026-09-14에 가중치를 내려받아 13건을 실제로 추론했다. 384차원과 노름 1을 실측으로 확인했다.

## 미결

- [x] `merchant-contents`·`merchant-vectors` 컬렉션을 발급의 개인화 신호에 연결했다. 현재 후보는 최신 내용 버전을, 목 소비 이력은 소비 당시의 내용 버전을 참조한다. 기존 5차원 목 벡터는 읽지 않는다. 연결과 갱신 방법은 [시드 안내](../data/seed/README.md)를 참고한다.

- [ ] 공공데이터포털 인증키를 발급받는다. 착한가격업소·상가(상권)정보 둘 다 인증키 없이는 한 행도 받을 수 없다. **대표메뉴 확보의 유일한 선행이다.**
- [ ] 내부 가맹점 ID와 공공 상가업소번호의 대응표를 만든다. 착한가격업소 조인의 선행이다.
- [ ] 착한가격업소와 상가(상권)정보의 매칭 규칙을 정한다. 공통 식별자가 없어 상호명·주소 정규화로 맞춰야 하고, 이 정확도가 벡터 품질의 상한이다.
- [ ] 좌표를 담을 필드를 어디에 둘지 정한다. `PersonalFitMerchantVector` 에는 좌표 자리가 없어 내용 레코드 쪽에 두거나 계약을 넓혀야 한다.
- [ ] 지역 라벨 포함이 업종·메뉴 구별력을 얼마나 희석하는지 측정한다. 지역 포함 전후의 순위를 같은 후보·이력으로 비교한다.
- [ ] 좌표를 거리 성분으로 어떻게 결합할지 정한다. 이 신호 안에서 곱할지, 별도 신호로 둘지가 열려 있다.
- [ ] ONNX 미러의 라이선스 표기 부재를 서류에 어떻게 적을지 정한다. 원본 MIT을 근거로 적되 표현을 확정해야 한다.
- [ ] 비AI 기준(업종 빈도, TF-IDF)과의 비교 조건을 고정한다. 임베딩의 기여를 말하려면 같은 후보·이력·난수가 필요하다.
