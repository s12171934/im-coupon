# D0 ↔ D1 업종 대응 기준

작성: 2026-09-15 · KAN-27

## 목적과 출처

D1 공공 상가의 소분류를 D0 소비 집계 업종에 연결하기 위한 **프로젝트 판단표**다. 공급자가 보증한 공식 변환표나 개별 가게의 카드사 등록 업종이 아니다.

- D1: `data/reference/store-codes.json`의 공공데이터포털 자료 `15012005`. 대분류 25개·중분류 266개·소분류 1,255개이며 업종 기준일은 2023-02-28이다.
- D0 정의 참고: [BC카드 공개 데이터 설명서](https://abp.bccard.com/dataContest/dataContestDetailPage?contestNo=9000001)의 업종 분류 상세. 저장소에 기록된 D0 11개 코드·명칭과 일치한다. 현재 사용하는 mock의 실제 생성 원본이 이 자료인지까지 확인한 것은 아니다.
- 사용자는 현재 데이터가 mock일 것이라고 설명했다. 이번 작업은 코드 대응만 정리하며 CSV 원본, 월별·지역별 관측 유무 및 mock 생성 과정을 검증하지 않았다.

전체 이름→코드, 양방향 목록, 현재 가게별 판정은 [전체표](D0-D1-업종-전체표.md)에 있다. 프로그램에서 읽을 자료는 `data/reference/d0-d1-category-mapping.json`이다.

초기 결과는 **대응 가능 17개·확인 필요 30개·미지원 1,208개**다. 현재 시드 12곳은 대응 가능 9곳·확인 필요 2곳·미지원 1곳이다. 이는 업종 판정 건수이며 실제 통계를 가진 가게 수가 아니다.

## 판정 규칙

| status | 의미 | d0Code | 통계 연결 |
| --- | --- | --- | --- |
| supported | 공개 정의와 D1 업종 범위로 하나의 대응을 제안할 수 있음 | 문자열 코드 | 실제 데이터 유무를 별도로 확인해야 함 |
| review_required | 분류가 겹치거나 영업 형태 확인이 필요함 | null | 후보 코드로 자동 대체하지 않음 |
| unsupported | 현재 11개 범위에 해당 영업 활동을 연결할 근거가 없음 | null | 미지원으로 반환 |
| unknown | 입력 코드가 기준 목록에 없거나 누락됨 | null | 입력·목록 갱신 확인; 미지원과 구분 |

`supported`도 프로젝트 추론이다. 명칭 유사도만 사용하지 않고 대·중·소분류의 영업 활동과 공개 상세 범위를 함께 비교했다. 제조·도매·전문 소매를 같은 상품의 음식점이나 슈퍼마켓으로 치환하지 않는다. 남은 분야는 분야별 제외 사유를 모든 행에 기록했다. `candidateD0Codes`는 검토 출발점이며 확정 매핑이나 배분 가중치가 아니다.

## 중요한 경계

- **카페 미지원이라는 이전 안내를 정정한다.** 공개 설명의 서양음식 범위에는 커피 영업도 있다. 카페의 D1 `I21201`은 D0 `8006`으로 제안한다.
- D0 한식 세 코드의 상세 설명은 동일하다. `I20101`처럼 백반과 한정식이 함께 있는 코드를 이름만 보고 `8003`으로 고정하지 않는다. 한식 세 코드 합산도 별도의 통계 설계가 필요하며 여기서는 수행하지 않는다.
- 횟집은 D1 한식 아래 있어도 상세 영업 기준으로 판단한다. 부모 분류만 보고 한식 통계에 넣지 않는다.
- 빵류·복합 디저트는 D0 범위가 겹치고, 대형 마트는 업태 경계가 불명확해 확인 필요로 둔다.
- 음식점과 주점, 할인 소매점과 제과 영업은 동일 상품을 취급해도 구분한다. 가게 이름 대신 공공 `categoryCode`를 사용한다.

## 결측과 mock 처리

자료 전체와 시드별 `statisticsAvailability`는 `not_checked`다. 업종 대응은 통계 존재 여부와 독립적이다. 대응 불가·확인 필요·관측 누락을 금액이나 회복 점수 **0으로 채우지 않는다**. 원자료에 실제 0이 관측된 경우와 결측은 구분해야 한다.

향후 소비 통계 조회는 다음 순서를 따른다.

1. 공공 소분류 코드를 전체표에서 찾는다. 없으면 `unknown`을 반환한다.
2. `supported`와 유효한 `d0Code`가 함께 있을 때만 D0 조회를 시도한다.
3. 동일 지역·업종·필요 월의 관측 여부를 확인한다. 없으면 `missing_statistics`처럼 사유를 반환한다.
4. mock 통계를 사용한다면 출처를 mock으로 명시하고 실제 상권회복의 증거로 설명하지 않는다.

이 표에는 매출·건수·회복 점수가 없다. 발급 점수, 신호 가중치, 후보 선택 로직도 이번 작업에서 변경하지 않는다. 후보 하나라도 결측이면 회복 신호를 요청 전체에서 끄는 정책은 후속 구현 대상이다.

## 갱신과 남은 확인

판정 원본은 `scripts/generate-d0-d1-crosswalk.mjs`이다. `node scripts/generate-d0-d1-crosswalk.mjs`로 로컬 기준 목록을 읽어 JSON과 전체표를 함께 생성한다. 인증키나 외부 요청은 사용하지 않는다. 생성 시 1,255개 코드의 중복·누락과 판단에 사용한 D0/D1 코드 존재 여부를 확인한다.

D1 목록 또는 D0 설명이 바뀌면 판단도 다시 검토해야 한다. 현재 1,255개라는 개수 확인만으로 명칭·범위 변경까지 탐지할 수는 없다. 생성 문서를 직접 편집하지 않고 스크립트의 판정과 이 안내를 수정한다.

다음은 실제 회복 신호 연결 전 필요한 작업이다.

- 현재 D0 mock의 필드·생성 규칙과 업종 코드 일치 여부 확인.
- 한식·복합 업종의 공급자 정의 또는 실제 카드 등록 업종 확보. 근거가 없으면 확인 필요 유지.
- 대전 지역·필요 월의 소비 통계 확보 및 결측 처리. D1 지역 목록과 소비 데이터의 지역 기준일·명칭도 별도로 대조.

자동 테스트·빌드·타입 검사는 실행하지 않았다. 데이터 생성 결과의 개수와 시드별 판정만 확인했다.
