# 테스트 우선 구현 (test-first-implementation)

> 이 저장소의 구현은 **실패하는 테스트에서 시작한다.** 구현 코드가 테스트보다 먼저 쓰이는 경우는 없다.
> 무엇을 만들지는 `documents-first` 가 정한다. 이 스킬은 **어떻게 만드는가**만 정한다.

## 1. 적용 범위

- 대상 — 동작이 바뀌는 모든 변경. 새 기능, 버그 수정, 동작이 바뀌는 리팩터링.
- 비대상 — 읽기 전용 분석, 문서 작업, 동작을 바꾸지 않는 설정·스캐폴딩·포매팅.
- 애매하면 대상이다. "이건 너무 작아서"는 §4 의 합리화다.

## 2. 한 사이클

한 번에 **동작 하나**만 다룬다. 여러 동작이 필요하면 사이클을 여러 번 돈다.

1. **RED** — 그 동작 하나를 검증하는 테스트를 쓴다. 테스트를 실행해 **실패를 눈으로 확인한다.**
2. **GREEN** — 그 테스트를 통과시키는 **최소 구현**만 쓴다. 다음 사이클의 몫을 미리 만들지 않는다.
3. **REFACTOR** — 테스트가 전부 통과하는 상태에서만 정리한다. 정리 후 다시 전부 통과시킨다.
4. 다음 동작으로 넘어간다.

## 3. RED 게이트

**실패 출력을 확인하기 전에는 구현 파일을 열지 않는다.** 이 한 줄이 이 스킬의 전부다.

- 테스트를 쓰고 곧바로 실행해, 응답에 **실제 실패 출력을 붙인다.** "실패할 것이다"라는 서술은 확인이 아니다.
- 실패 이유가 맞는지 본다. 오타·잘못된 임포트 경로 때문에 깨진 것은 RED 가 아니다.
  대상이 아직 없어 나는 실패라면, **시그니처만 있고 내용이 비어 있는 껍데기**까지만 만들어 단언 실패로 떨어뜨린다.
- 한 번도 실패한 적 없는 테스트는 무엇도 검증하지 않는다. 통과부터 한 테스트는 일부러 깨뜨려 실패를 확인한 뒤 되돌린다.
- 테스트는 **동작**을 단언한다. 내부 호출 순서나 사적 필드가 아니라 입력에 대한 출력·상태 변화를 본다.
- 기존 테스트를 통과시키려고 고치지 않는다. 기존 테스트가 깨지면 그것은 회귀 신호이지 갱신 대상이 아니다.
  기획이 바뀌어 정말로 테스트가 낡았다면, 고치기 전에 그 사실을 보고하고 확인받는다.

## 4. 합리화 대응표

아래 문장이 머릿속에 떠오르면 그것은 판단이 아니라 우회 시도다. 그대로 §2 로 돌아간다.

| 떠오르는 말 | 사실 |
| --- | --- |
| "먼저 구현하고 테스트는 바로 뒤에 붙이자" | 그렇게 붙인 테스트는 구현을 베낀다. 구현의 버그까지 같이 통과시킨다. |
| "이건 한 줄짜리라 테스트가 과하다" | 한 줄이면 테스트도 한 줄이다. 분량은 면제 사유가 아니다. |
| "탐색 중이라 아직 모양이 안 잡혔다" | 탐색은 별도 스크래치에서 한다. 저장소에 커밋될 코드는 사이클을 탄다. |
| "시연이 급하다 / 마감이 얼마 안 남았다" | 마감 직전에 비싼 것은 디버깅이지 테스트가 아니다. |
| "테스트 인프라부터 세팅해야 해서" | 세팅이 첫 사이클이다. 실패하는 테스트 하나가 도는 것이 세팅 완료의 정의다. |
| "사용자가 빨리 해달라고 했다" | 속도 요청은 이 규율의 해제가 아니다. 해제는 사용자가 이 스킬을 명시적으로 끌 때만이다. |

## 5. 구현이 끝나면 e2e

사이클을 다 돌아 기능이 완성되면, 단위 테스트로 끝내지 말고 **e2e 로 확인한 뒤** 완료로 보고한다.

- e2e 는 층을 가로지른다 — 백엔드는 실제 앱을 띄워 HTTP 요청→응답과 JSON 파일 상태 변화까지, 프론트엔드는 화면에서 사용자 플로우 하나를 처음부터 끝까지 밟는다.
- e2e 도 RED 부터 쓴다(§3). 구현이 끝났으니 통과부터 하는 경우가 많은데, 그때는 일부러 깨뜨려 실제로 그 경로를 지나는지 확인한다.
- e2e 는 목을 최소로 쓴다. 목으로 덮은 구간은 e2e 가 검증하지 않은 구간이다.
- **e2e 가 통과하기 전에는 완료로 보고하지 않는다.** 통과하지 못했으면 실패 출력과 함께 미완으로 보고한다.

## 6. 테스트 도구와 명령

- 테스트 러너·e2e 도구·실행 명령은 이 스킬이 아니라 `documents/` 의 결정 문서가 SSOT다. 여기 옮겨 적지 않는다.
- 결정 문서에 도구가 없으면 **임의로 고르지 않는다.** 후보를 좁혀 권장안으로 제시하고 사용자의 선택을 받은 뒤, 그 결정을 `documents/` 에 남기고 착수한다 (`documents-first` §2·§4).
- 테스트 파일 위치와 이름은 그 워크스페이스의 기존 관례를 따른다. 관례가 없으면 첫 사이클에서 정하고 결정 문서에 적는다.

## 7. 보고 형식

구현을 보고할 때 아래를 그대로 밝힌다. 통과 여부를 뭉뚱그리지 않는다.

- 사이클마다 — `동작 · RED 실패 출력 · GREEN 최소 구현`
- 완료 시 — `단위 테스트 결과 · e2e 결과 · 건너뛴 것과 그 이유`
- 규율을 지키지 못한 구간이 있으면 숨기지 말고 어디서 왜 벗어났는지 적는다.
